## 1. card_access_log の仕様
- 記録するのは「カードを開いた」1種類のみ。
- **列は5つ**: `id` / `short_id` / `accessed_at` / `user_id` / `ua`
- **IPは取得していない**（2026-08-03確認・列が存在しない）。
  後付けも簡単ではない。`log_card_access` はフロントから呼ぶRPCで、
  ブラウザは自分の接続元IPを知らない。サーバ側で拾うなら Edge Function を挟むか
  `inet_client_addr()` だが、後者はプール経由でゲートウェイのIPが入る可能性が高い（未実測）。
  ※取るかどうかは思想の判断が先。IPはプライバシー度が一段上がり、
    何を取り・何に使い・何日で消すかをプラポリに明記する必要がある。
    目的は障害調査／不正アクセス調査に限る。
- `accessed_at` は **UTC保存**。閲覧時に JST 変換する（保存はUTC＝DB標準、表示だけJST）。
  **SQLを書くたびに `at time zone 'Asia/Tokyo'` を付ける**。

## 2. 記録の仕組みと既知の欠陥（2026-08-07 実読で確定／2026-08-15 修正）
- 呼び出しは **receive.html 361行の1箇所のみ**。`get_card` 成功直後、
  状態判定（closed／is_blank／is_owner／未確定）の**手前**。
  したがって**未ログインを弾く枝も、QR型／URL型で分ける枝も存在しない**。
  ※当初の仮説「QR型の未ログイン経路が構造的に抜けている」は**否定された**。
- ✅**二重カウントは2026-08-15に解消**。原因＝receive.html 397行で `data.is_owner` なら
  card.html へ `location.href` で飛ぶ。ログを取った後に飛ぶため card.html 側でも
  もう1件入っていた（0.4秒ペアの正体）。**card.html 1269行の呼び出しを削除**して解決。
  実機確認＝#265 を receive 経由で開き card.html へ遷移 → **ログ1件のみ**（08-15 05:58）。
- ✅**エラーの握り潰しも2026-08-15に解消**。`.then(null, () => {})` を console.error 付きへ。
  **supabase-js v2 はHTTPエラーで reject しない**ため、`error` フィールドの明示チェックと
  例外ハンドラの両方を設置した。
  ※これは**可視化**であって取りこぼしの修理ではない。**今後の失敗は見えるが、過去分は復旧不可**。
- ⚠**取りこぼしは未解決**。実例は下記「読み方の鉄則」1を参照。
- **開くたびに1件入る**。1人が何件も出す（2026-08-07・受け手Aが26分で14件）。

### 読み方の鉄則
1. **「記録が無い＝開かれていない」と読んではいけない**。
   実例：#256（4yoftg・QR型）は受け手が開いたことが確実なのにログに無い。
   **2026-08-15に2件目の疑いが出た**（受け手Aが「連打の前に一度見た」と証言しているが、
   その時刻に該当する記録が無い）。**取りこぼしは単発の事故ではない前提で読む**。
2. **件数＝人数ではない**。数えられるのはアクセス回数のみ。
3. **UAによる本人判別は補助**。iOS 17以降はプライベート系設定やロックダウンモードで
   UAが丸められることがある。**判別の主軸は user_id**。
4. **未ログイン件数は実態より少なく出ている前提**で読む。

## 3. 保存クエリ

### ★ ①日別サマリ（直近14日・FAVORITESへ）
```sql
-- 運営ダッシュボード：日別サマリ（過去14日・JST）
with d as (
  select generate_series(
    (now() at time zone 'Asia/Tokyo')::date - 13,
    (now() at time zone 'Asia/Tokyo')::date, '1 day')::date as 日付
),
u as (select (created_at at time zone 'Asia/Tokyo')::date d, count(*) n
      from auth.users group by 1),
r as (select (created_at at time zone 'Asia/Tokyo')::date d, count(*) n
      from rooms where bundle_id is null group by 1),
m as (select (created_at at time zone 'Asia/Tokyo')::date d, count(*) n
      from room_posts where post_type = 'message' group by 1),
p as (select (created_at at time zone 'Asia/Tokyo')::date d, count(*) n
      from room_posts where post_type = 'reply' group by 1),
c as (select (closed_at at time zone 'Asia/Tokyo')::date d, count(*) n
      from rooms where closed_at is not null group by 1),
t as (select (transferred_at at time zone 'Asia/Tokyo')::date d,
             count(*) filter (where transfer_type = 'reply_claim') as n,
             count(*) filter (where transfer_type = 'discard')     as x
      from room_transfers group by 1),
a as (select (accessed_at at time zone 'Asia/Tokyo')::date d, count(*) n
      from card_access_log
      where user_id is null
         or user_id not in ('<運営UUID-1>', '<運営UUID-2>')
      group by 1)
select d.日付,
  coalesce(u.n,0) as 新規登録, coalesce(r.n,0) as 部屋作成,
  coalesce(m.n,0) as 確定, coalesce(p.n,0) as 返信,
  coalesce(t.n,0) as claim, coalesce(t.x,0) as 破棄,
  coalesce(c.n,0) as 終了, coalesce(a.n,0) as アクセス
from d
left join u on u.d=d.日付  left join r on r.d=d.日付
left join m on m.d=d.日付  left join p on p.d=d.日付
left join c on c.d=d.日付  left join t on t.d=d.日付
left join a on a.d=d.日付
order by d.日付 desc;
```
> **`<運営UUID-1>` `<運営UUID-2>` はこのMDには書かない**（publicリポジトリのため）。
> 実値は Supabase の保存クエリ側に入れてある。運営2アカウントの user_id。

### ②アクセス明細（誰が／端末）
```sql
select
  l.accessed_at at time zone 'Asia/Tokyo' as 日時,
  r.global_no,
  l.short_id,
  case
    when r.claimed_at is not null and l.accessed_at < r.claimed_at
                                 then '※前の代'
    when l.user_id is null       then '相手（未ログイン）'
    when l.user_id = r.user_id   then '自分'
    else                              '相手（登録者）'
  end as 誰が,
  case
    when l.ua like '%Android%'   then 'Android'
    when l.ua like '%iPhone%'    then 'iPhone'
    when l.ua like '%iPad%'      then 'iPad'
    when l.ua like '%Windows%'   then 'PC'
    when l.ua like '%Macintosh%' then 'Mac/iPad'
    when l.ua like '%Linux%'     then 'PC(Linux系)'
    else 'その他'
  end as 端末,
  substring(l.ua from 'iPhone OS ([0-9_]+)') as iOS,
  case
    when l.ua like '%Line/%' and l.ua like '%IAB%' then 'LINE(Android)'
    when l.ua like '%Line/%'                       then 'LINE(iOS)'
    else ''
  end as アプリ内
from card_access_log l
join rooms r on r.short_id = l.short_id
where l.accessed_at > now() - interval '30 days'
order by l.accessed_at desc;
```
- 特定カードだけ見たい時は `and r.global_no = 268` を足す。
- **UA全文を見たい時は `l.ua` をそのまま出す**。末尾に `Line/` があれば LINE内蔵ブラウザ。
- **iOS列が本人判別の決定打**（2026-08-15追加）。運営端末は 26_5_2 →
  2026-08-12以降 26_6_0。**それ以外の値が出たら外来端末**と一目で分かる。
  この列が無かったため、8/03の1件を運営自身のアクセスと誤って記録していた期間がある。
- **端末列は目安**。CASEは上から評価されるため Android を先頭に置いている
  （両方含むUAを Android 側で拾う予防）。
  ※ただし**実測では Android と iPhone を両方含むUAは全期間で0件**＝
    この並べ替えは予防であって、過去の誤判定を直したものではない。
  ※**iPadOS 13以降は UA が `Macintosh` を名乗る**ため、Mac と iPad は文字列では分離不可。
  ※証拠として使うなら**必ず生UAを見ること**。
- **判定軸は owner_user_id ではなく user_id（作成者）**。claim で owner は書き換わるため、
  owner を使うと持ち主が代わった瞬間に判定が反転する。
- **世代交代をまたぐと判定できない**。card_access_log は short_id しか持たず、
  claim で short_id が新部屋へ付け替わるため、旧世代のログが丸ごと新部屋にぶら下がる。
  境界は新部屋の `claimed_at` で切り、それ以前は「※前の代」として逃がす。
  厳密にやるなら room_transfers の移管時刻と突き合わせるが、**必要になってから作る**。

## 4. SQLの読み方（2026-08-12確定）
- **確定は `room_posts` の message 時刻が代理指標**。rooms に確定日時の列が無いため。
- **部屋作成は `bundle_id is null` で束生成を除外**する。しないと束を作った日に跳ねる。
- **アクセスは自分を除外して初めて意味を持つ**。
  除外前の実測＝8/03 **61件** ／ 8/02 **35件** ／ 8/11 **11件**。ほぼ全部TAKAの開発作業。
  除外後の外部アクセスは**14日間で2日分・18件のみ**。
- **未ログインでの自己テストは除外できない**（user_id が無いため）。
- アクセスは二重カウント＋取りこぼしあり。**回数であり人数でもない。意味づけしない**。
- 破棄は `room_transfers.transfer_type = 'discard'` で取れる（下記6参照）。

## 5. 取得種類の拡張候補（何を残すか＝思想と要相談）
「保全・裏方ログに限る」線を死守する。
- カードを開いた（現状・閲覧）
- 確定した（送り主が is_confirmed=true にした瞬間）
- 返信が来た（受け手が reply 投稿）
- お役目終了／名刺破棄した
- claim した（所有権移転＝バトンの1歩・room_transfers と重複の要否）
- 協賛抽選が回った（御朱印付与の記録）

※評価装置を置かない原則との両立に注意。ログは「誰が触ったか」を表に出すためでなく、
  運営の保全・障害調査のための裏方に限る。**公開UIには出さない**。
※**開封数を協賛先やユーザーに公表する予定は無い**。直す理由も見る理由も
  「運営が状態を正しく把握するため」。実際にClaudeが
  「#256はまだ一度も開かれていない」と誤断した。
※**導入前にプライバシーポリシーへの記載が要る**。
