## 2. 確認リンクの期限切れ（⚠未対処・Web側のため印刷後で可）

**設定値**: `Email OTP expiration` = **3600秒（1時間）**。
場所は Authentication → Sign In / Providers → Email の中。
`Confirm email` は **ON**（＝確認しないとログインできない）。

**期限切れリンクを踏むとどうなるか（実測）**

着地先は
`auth.html#error=access_denied&error_code=otp_expired&error_description=Email+link+is+invalid+or+has+expired`。
しかし**画面には何のエラーも表示されない**。通常のログイン画面にしか見えない。
エラー情報はURLのハッシュにあるだけで、auth.html がそれを読んでいない。

**その状態でログインを試すと**

「メールの確認が完了していません。届いたメールのリンクをクリックしてください」
と日本語で表示される（実装済み）。
**ただしこの指示は実行不可能**——そのリンクは既に失効している。
踏む→何も起きない→ログインする→また同じ指示、で**永久ループになる**。

**自力脱出は可能（実測）**

新規登録タブで**同じメールアドレスを再入力すると確認メールが再送される**。
Supabase の仕様（未確認アドレスの再 signUp はエラーを返さず再送する。
「既に登録済み」と返すとアドレスの存在が漏れるため）。
2026-08-21 に実際に再送を確認した。

**問題は導線がゼロなこと**。「新規登録をもう一度やる」という脱出路は
画面のどこにも書かれていない。受け手が自力で思いつく可能性は低い。

**対処案（優先順・いずれもWeb側／印刷後で可）**

1. ログイン失敗時の文言に「有効期限1時間・切れた場合は新規登録から
   同じアドレスで登録すると再送される」を追記する。**実装不要・文言のみ**
2. auth.html でURLハッシュの `error_code=otp_expired` を読み、期限切れバナーを出す
3. `Email OTP expiration` を延長する（3600 → 21600 or 86400）。設定のみ・可逆

**2026-08-21時点の判断**: **③は実施しない。現状を記録するに留める**（TAKA判断）。
自力脱出できると分かった以上、期限を伸ばすより文言を直すほうが本質的なため。

## 4. ユーザー削除時の挙動（実測 2026-08-21）

**delete_rule の実測値**

| 表 | 列 | delete_rule |
|---|---|---|
| profiles | id | **CASCADE** |
| rooms | owner_user_id | NO ACTION |
| rooms | bundle_id | NO ACTION |
| room_posts | user_id | NO ACTION |
| room_transfers | room_id | NO ACTION |
| **rooms** | **user_id** | **外部キー自体が存在しない** |

確認に使ったSQL（`profiles` の部分。表名を変えれば他も見られる）:

```sql
select
  tc.table_name,
  kcu.column_name,
  rc.delete_rule
from information_schema.table_constraints tc
join information_schema.key_column_usage kcu
  on kcu.constraint_name = tc.constraint_name
join information_schema.referential_constraints rc
  on rc.constraint_name = tc.constraint_name
where tc.table_schema = 'public'
  and tc.constraint_type = 'FOREIGN KEY'
  and tc.table_name in ('profiles','rooms','room_posts','room_transfers');
```

**CASCADE の実証**

テスト垢2件を Authentication → Users → Delete user で削除。
`auth.users` 7→5件、`public.profiles` も5件で一致。**孤児行は発生しない**。

**`rooms.user_id` に外部キーが無いのは意図どおり（TAKA判断・2026-08-21）**

`user_id` は「最初にその部屋を作った人」を指す。
**その人が退会しても、部屋の履歴としては残したい**。
よって制約を掛けないのが正しい。**バグではない**。

**ただし現状は噛み合っていない**

`owner_user_id` が NO ACTION のため、**部屋を持っているユーザーは
そもそも削除できない**。「履歴を残したい」という意図に対して、入口で止まる。

→ 将来 `owner_user_id` を **SET NULL** に変更すれば
「持ち主は消えたが、部屋と作成者の記録は残る」となり意図と一致する。
退会機能が存在しない現在は急がない。**大掃除リスト＋決定台帳の候補**。

**運用上の注意**: テスト垢を作る際は**部屋を作らないほうが後始末が楽**。
部屋を作ると owner_user_id で引っかかり、垢を消す前に部屋を消す手順が要る。

## 5. 触らないと決めた設定（2026-08-21確認）

- **Secure password change = OFF のままでよい**。
  ONにすると「パスワード変更に再認証が要る（24時間以内のログインなら免除）」
  という緩和つきの制限が入る。ただし `Require current password when updating`
  が既に **ON** で、現在のパスワードを知らないと変更できない。二重で過剰。
  ※将来 `Require current password` を OFF にするなら、
    Secure password change は ON にすること。**セットで考える2つ**
- **Prevent use of leaked passwords** は Pro plan 限定のため選べない
- **Security通知7本**（パスワード変更・メアド変更・MFA等）はすべて OFF のままでよい。
  ONにすると送信数が増えるだけで、現段階では必要ない
