# カード状態遷移 統合メモ（2026-07-04）

位置づけ：複数チャットに散っていたclaim・所有権・期限の議論を全履歴（「完。」含む）横断で照合し、一本化したもの。これが状態遷移の正。以後この件で過去チャットを掘り直さない。

## 1. 二層構造（大前提）

- **カード層（short_id）**＝物理現物の一生。半永久、汚れ・破損まで
- **部屋層（room）**＝1ターン完結の心の往復。カード1枚の上で世代交代していく

---

## 2. カード層の状態遷移

```
[白紙] --claim--> [所有中] --（部屋の往復を繰り返す）--> [供養済み/木へ]（終着）
   ^                  |
   └--（上書き例外）--┘
```

### 状態
1. **白紙**：印刷済み・持ち主なし。店頭の束＝店の在庫（誰のものでもない）
2. **所有中**：誰かがclaim済み。バトンで所有は移転していく
3. **供養済み**：short_idを閉じる（6/5決定）。再スキャンで「供養済み」表示。物理カードは残しても捨てても本人の自由。木に短冊として納まる（奉納）
   - ※「閉じる」は**番号を再利用しない前提**でのOK（7/4確認）。保留中の**永久カード構想**（期限切れ時にshort_idを未claim解放しリレー継続）とは衝突する：閉じる＝カードに一生の終わりがある／解放＝カードは死なずリレー継続。可逆なので本番前に最終決定。現時点の実装は「閉じる」で進めてよい

### claimの3経路（これ以外で所有権は絶対に動かない）
| 経路 | 誰が | トリガー | 備考 |
|---|---|---|---|
| A. 白紙claim | 白紙カードを拾った人 | 確認画面「このカードはまだ白紙です。あなたのカードにしますか？」→明示ボタン | スキャン即claim禁止の原則 |
| B. 親QR一括claim | 束の撒き手（スポンサー等） | 親QRスキャン→一括 | 物理占有＋親スキャン＝所有意思。一度きり（claim後ロック） |
| C. 返信claim | 書かれたカードを受け取った人 | **返信した瞬間**（2026-07-04確定） | 心の往復＝所有の移動。案4採用 |

### 親QR一括claimの詳細（2026-07-04確定）
- **claim済みの子はスキップ**（デフォルト）。未claim分のみ一括
- スキップした番号を画面に表示：「10枚中9枚claimしました。No.003はclaim済みです」
- 「束の中にNo.003の現物はありますか？」の確認UI
  - **ある** → 異常混入（テスト・検品・印刷屋事故）。「白紙に戻して再claim」ボタン→二段確認→上書き実行
  - **ない** → 正規の持ち主が保有中。何もしない（絶対に奪わない）
- 判定できるのは現物を見ている人間だけ。システムは自動判定しない

## 3. 部屋層の状態遷移

```
[空] --A記入・確定--> [送信済み] --B返信--> [完結]
                          |                    |
                          |               （B＝新所有者。次ターンへ）
                     （返信なし＝招待状態のまま）
```

- 1部屋1ターン完結・確定後は修正不可（不可逆）
- Bの返信も1回きり・修正不可
- **次ターンのトリガー＝返信**。B返信→Bが所有者→同じshort_idで新しい部屋が立つ→Bが次のAになれる
- 返信スタート/送信スタートの分岐は部屋の初期状態（中身の有無）で動的に決まる。別システム不要
- 開くだけ（view）は誰でも可・送り主に通知しない。「黙ってやったことは越境しない、自分の意思の返信だけが越境する」

## 4. 期限設計（2026-06-14確定・二段構え）

- **バトン期限＝2ヶ月**（表に見せる「使える期限」。新規に渡せるのはここまで）
- **完走猶予＝＋1ヶ月**（最終日近くの1ターンが受領・返信を終えるための余白。新規バトン不可）
- **3ヶ月目の末＝完全処理**（表示期限と実処理が一致・スポンサー四半期と整合）

### 終着4パターン
1. **回す** → 旅が続く（終着でない）
2. **破棄を選ぶ** → 人の手で供養 → 木へ
3. **空部屋・編集中のまま期限**（白紙／claim済み未記入含む） → クウが供養して木へ
4. **送信済み・返信なしのまま期限** → 猶予1ヶ月 → **カードを閉じ、返信も閉じる**（3ヶ月で完全に締まる）→ クウが供養して木へ（7/4確定）
   - 短冊は**「ありがとう」のみ**。「届かなかった」系の文言は使わない
   - 理由：既読を取らない設計上、読まれたか否かはシステムに分からない。「届かなかった」は半分嘘になり得るが「ありがとう」はどちらでも真。カード（スポンサーの協賛で生まれた名刺）が果たした仕事への感謝＝名刺に罪はない
   - 本文（私信）は絶対に木に出さない・送り主に通知しない（黙る＝push通知しないの意。Aが後で部屋を見に来たら供養済みが分かるpull型）
   - 部屋は凍結viewで残る（読める・心は消えない。返信だけ不可）

- 期限処理＝claim枠の解放装置でもある（在庫詰まり防止）。pg_cron日次バッチで実装可
- 木に掛かるのは「木宛て投稿」だけ。書き手は人間かクウの二種。部屋の中身は何があっても木に出ない

## 7. 動かさない原則（再掲）

- スキャン即claim禁止（子QR）。viewとclaimは完全分離
- 誰かの所有カードをシステムが自動で奪うことは絶対にない
- 黙ってやったことは送り主に通知しない
- 来なくても責めない（放置は罪でない。クウが引き取るだけ）
- 決めるは可逆、焼くは不可逆（番号体系・QR印刷は最後に確定）
