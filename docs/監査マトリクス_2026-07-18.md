## 第2次監査（2026-07-20・EXECUTE権限×内部ガードの層）
第1次で未走査やった「RPCを誰が叩けるか（EXECUTE）×中の門番」を全18本走査。

| 発見 | 対処（2026-07-20実施済み） |
|------|------|
| create_bundle / create_bundle_v2: 「auth.uid()がnullならSQL Editor」前提のガードが、anonキーのREST直叩き（同じくuid=null）に素通し。束量産が可能やった | v1: 全ロールrevoke（dead code）。v2: anonをrevoke（authenticated＋is_operator()で防御成立） |
| handle_new_user / generate_short_id: 内部専用（トリガー/definer内部呼出）に外部EXECUTE付与 | anon/authenticatedからrevoke |
| delete_room / reset_blank_and_claim: 内部ガード健全・anon付与は無駄なだけ | 最小権限化でanonをrevoke |
| 軽微件①（レガシーposts緩いINSERTポリシー）が現存確認 | DROP POLICY実施（大掃除リストから消化済み） |

第2次で全RPCの内部ガードを判定済み: claim系5本＝仕様通りanon可（受け取り前アクセス）、
create_my_bundle/mark_bundle_printed/get_my_bundle_prints＝auth.uid()スコープで自己完結、
get_bundle_info/get_card＝token/key保持者のみ、log_card_access＝仕様。全✅。

## 教訓（次の関数を書く時のルール）
- 「auth.uid() is null＝SQL Editor」の前提は誤り。anonキーREST直叩きでもnullになる。
  definer関数の管理者ガードはEXECUTE権限側で絞るのが確実
- Postgresは関数作成時にPUBLICへEXECUTEを自動付与する。新RPC作成時は
  revoke→必要ロールにgrantを儀式化する
